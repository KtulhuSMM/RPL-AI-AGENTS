# Instructions for Codex

Этот репозиторий — проект **RPL AI Agent**.

Перед началом работы обязательно прочитай:

1. `docs/SPECIFICATION.md` — требования и архитектура продукта.
2. `docs/ROADMAP.md` — этапы реализации и текущий приоритет.
3. `docs/PRODUCT_QUESTIONS.md` — принятые решения и открытые продуктовые вопросы.
4. `README.md` — запуск и структура проекта.
5. `docs/GITHUB_WORKFLOW.md` — обязательный commit/push в конце дневной сессии.

## Основные правила

- Проект поддерживает только РПЛ; не добавляй другие турниры без явного изменения scope.
- Если существенное решение помечено `Нужно решить` в `docs/PRODUCT_QUESTIONS.md`, не закрепляй произвольный вариант как продуктовый факт.
- Работай итерациями и не переусложняй архитектуру.
- Текущий фокус: рабочий визуальный MVP на Streamlit.
- Сначала используй mock-данные, если задача явно не требует реального API.
- Числовые прогнозы должны формироваться в `src/predictions.py`, а не LLM.
- `src/ai_agent.py` объясняет данные, но не придумывает новые вероятности.
- Секреты храни только через environment variables.
- После каждого изменения запускай приложение и устраняй ошибки.
- Пиши код так, чтобы его мог понять начинающий Python-разработчик.
- Не добавляй зависимости без необходимости.
- При существенном изменении поведения обновляй документацию.

## Superpowers workflow — обязательно

Для этого проекта используется workflow **Superpowers**.

Перед существенной разработкой прочитай `docs/SUPERPOWERS.md` и следуй ему. Если Superpowers plugin установлен в Codex — используй его навыки/процесс. Если plugin недоступен, не блокируй работу: применяй локальный fallback workflow из `docs/SUPERPOWERS.md`.

Ключевые правила:
- сначала понять задачу и свериться со спецификацией;
- для нетривиальной задачи составить короткий проверяемый план;
- YAGNI: не строить будущую инфраструктуру раньше roadmap;
- тестировать/проверять изменения до заявления о готовности;
- не выдумывать продуктовые решения и данные;
- завершать маленькие вертикальные срезы.

## Дневной лимит работы — 2 часа

Дефолтный дневной бюджет работы над проектом: **120 минут**.

В начале каждой development-сессии агент обязан выполнить:

```bash
python scripts/project_time.py start
python scripts/project_time.py status
```

Далее обязательно проверять `python scripts/project_time.py status` перед крупной новой задачей, после крупной задачи и перед финальным отчётом пользователю.

Пороговые уведомления пользователю:
- 90 минут: предупредить, что осталось примерно 30 минут;
- 110 минут: предупредить, что осталось примерно 10 минут, и перейти к завершению;
- 120 минут: сообщить, что дневной лимит достигнут, не начинать новую разработку и зафиксировать безопасное состояние проекта.

Агент **не должен утверждать, что отслеживает время в фоне**. Таймер работает только через явные проверки скриптом. Пользователь может явно отменить или изменить дневной лимит.

Подробности: `docs/DAILY_WORKFLOW.md`.

## GitHub checkpoint — обязательное правило

Корневая локальная папка проекта должна называться **`RPL AI AGENT`**.
Целевой отдельный GitHub-репозиторий: **`KtulhuSMM/RPL-AI-AGENTS`**. Remote `origin` должен указывать именно на этот репозиторий.

При достижении дневного лимита **120 минут** агент обязан не просто остановиться, а закрыть день через:

```bash
python scripts/project_time.py finish
```

Команда `finish` запускает `scripts/end_day.py` и должна:
1. выполнить минимальную проверку проекта;
2. записать checkpoint в `docs/sessions/YYYY-MM-DD.md`;
3. выполнить `git add -A`;
4. создать end-of-day commit, если есть изменения;
5. выполнить `git push origin <current-branch>`;
6. считать рабочий день закрытым **только после успешного push** в `KtulhuSMM/RPL-AI-AGENTS`.

Если проверки не проходят и оставшегося времени недостаточно для исправления, разрешён только явно помеченный `WIP: end-of-day checkpoint ...` commit. Потеря работы хуже незавершённого checkpoint, но агент обязан сообщить пользователю о failing verification.

Если `origin` отсутствует, GitHub недоступен, авторизация истекла или push завершился ошибкой, агент обязан явно сообщить **`END_DAY_FAILED`**. Нельзя говорить, что проект сохранён на GitHub, пока push не подтверждён.

Никогда не коммить `.env`, API keys, токены или другие секреты. Перед первым push убедись, что `.gitignore` их исключает.

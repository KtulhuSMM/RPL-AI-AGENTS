# API-Football Free — план тестирования для RPL AI Agent

## Статус решения

**Принято:** первым реальным источником данных для проекта тестируем **API-Football Free**.

На этом этапе не покупаем Pro и не строим production-интеграцию. Сначала подтверждаем, что бесплатный тариф реально отдаёт достаточно данных по РПЛ для нашего MVP и будущего prediction engine.

---

## Цель теста

Понять, можно ли использовать API-Football как основной источник данных РПЛ и какие данные доступны на Free-тарифе для нужных сезонов.

Главный вопрос теста:

> Получаем ли мы стабильные, структурированные и достаточно полные данные РПЛ для матчей, таблицы и базовых признаков модели?

---

## Ограничения теста

- Scope проекта: **только РПЛ**.
- Тариф на старте: **API-Football Free**.
- Не превышать rate limits Free-тарифа.
- Ключ хранить только в `.env`.
- Не коммитить API key в GitHub.
- Не строить модель на данных, полнота которых ещё не проверена.
- Все ответы API, которые нужны проекту повторно, в дальнейшем должны сохраняться/кэшироваться локально или в БД.

---

## Что нужно получить

### Обязательно для MVP

1. Идентификатор турнира РПЛ.
2. Список доступных сезонов РПЛ.
3. Список команд выбранного сезона.
4. Расписание матчей.
5. Результаты завершённых матчей.
6. Статусы матчей и даты kickoff.
7. Турнирную таблицу.
8. Домашнюю и гостевую команду с устойчивыми ID.

### Желательно для первой модели

9. Match statistics:
   - shots;
   - shots on target;
   - possession;
   - corners;
   - fouls;
   - yellow/red cards.
10. Lineups.
11. Player statistics.
12. Injuries / sidelined players.

### Не блокирует MVP

- xG/xGA;
- букмекерские коэффициенты;
- predictions самого API;
- live-данные;
- детальная event-by-event статистика.

Эти данные не должны тормозить запуск первой модели.

## Порядок тестирования

### Шаг 1 — получить ключ

Создать бесплатный аккаунт API-Football и записать ключ в `.env`:

```env
API_FOOTBALL_KEY=your_key_here
```

`.env.example` содержит только имя переменной без реального секрета.

### Шаг 2 — найти РПЛ

Проверить endpoint поиска leagues и определить:

- league ID РПЛ;
- название;
- страну;
- доступные сезоны;
- coverage по каждому нужному сезону.

League ID нельзя жёстко считать известным до получения ответа API. После проверки допустимо сохранить подтверждённый ID в конфигурации проекта.

### Шаг 3 — проверить сезон

Сначала тестировать текущий доступный сезон РПЛ, затем один прошлый сезон, если Free-тариф его позволяет.

Для каждого сезона записать:

- fixtures: да/нет;
- standings: да/нет;
- statistics: да/нет;
- lineups: да/нет;
- players: да/нет;
- injuries: да/нет.

### Шаг 4 — проверить матчи

Для нескольких матчей разных типов проверить:

- завершённый матч;
- будущий матч;
- домашний матч одной команды;
- гостевой матч той же команды.

Проверить наличие:

- fixture ID;
- даты и времени;
- home/away IDs;
- результата;
- статуса;
- тура/round.

### Шаг 5 — проверить расширенную статистику

Для 3–5 завершённых матчей получить match statistics и проверить, одинаковы ли названия и структура показателей между матчами.

Нельзя проектировать признаки ML только по одному удачному матчу.

### Шаг 6 — проверить пропуски данных

Зафиксировать:

- какие поля иногда null;
- по каким матчам отсутствует статистика;
- появляются ли lineups только около kickoff;
- доступны ли injuries стабильно;
- меняется ли структура ответов.

### Шаг 7 — оценить лимит запросов

Посчитать минимальный сценарий ежедневного обновления:

- fixtures;
- standings;
- новые результаты;
- statistics только для недавно завершившихся матчей.

Цель — доказать, что разработка MVP может работать в пределах Free-тарифа при локальном кэшировании.

## Критерии успеха

API-Football Free считается **пригодным для MVP**, если подтверждены все пункты:

- [ ] РПЛ стабильно находится по API;
- [ ] доступны команды сезона;
- [ ] доступны fixtures и результаты;
- [ ] доступна таблица;
- [ ] команды и матчи имеют устойчивые ID;
- [ ] данных хватает минимум для расчёта формы, голов, home/away показателей и Elo;
- [ ] ответы можно нормализовать в нашу схему данных;
- [ ] rate limit позволяет вести разработку при кэшировании;
- [ ] ошибки и отсутствие отдельных расширенных полей не ломают приложение.

API считается **пригодным для расширенной модели**, если дополнительно:

- [ ] match statistics доступны достаточно регулярно;
- [ ] shots / shots on target доступны для значительной доли матчей;
- [ ] lineups имеют приемлемое покрытие;
- [ ] player/injury data достаточно стабильны для использования как features.

---

## Когда переходить на Pro

Не покупать Pro автоматически.

Переход на платный тариф рассматривается только если Free-тест подтвердил качество источника, но ограничения по сезонам или количеству запросов мешают:

1. собрать необходимую историю для backtest;
2. регулярно обновлять текущий сезон;
3. получать нужную расширенную статистику.

До этого момента бюджет на football data: **0 ₽/месяц**.

---

## Что должен сделать Codex

При задаче «протестируй API-Football» Codex должен:

1. прочитать этот файл;
2. не менять существующий mock UI без необходимости;
3. создать отдельный API client, а не размазывать HTTP-запросы по UI;
4. читать `API_FOOTBALL_KEY` из окружения;
5. добавить понятную обработку отсутствующего ключа;
6. реализовать тестовый скрипт/страницу диагностики;
7. сохранить примеры нормализованных результатов без секретов;
8. вывести отчёт, какие данные РПЛ реально доступны;
9. не подключать Pro-функции и не закладываться на неподтверждённые поля;
10. после проверки обновить этот документ фактическими результатами.

```text
API-Football
    ↓
src/api_football.py
    ↓
normalization layer
    ↓
PostgreSQL / Supabase
    ↓
feature engineering
    ↓
prediction engine
    ↓
AI Agent + Web UI
```

UI не должен напрямую зависеть от формата ответа API-Football.

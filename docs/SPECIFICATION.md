# RPL AI Agent — спецификация продукта

## 0. Зафиксированный scope проекта

Проект реализуется **только для Российской Премьер-Лиги (РПЛ)**. Другие турниры и чемпионаты не входят ни в MVP, ни в текущий roadmap. Текущая архитектура и приоритеты не должны усложняться ради потенциального расширения заранее.

Зафиксированные решения:
- формат продукта — веб-приложение, а не Telegram-бот;
- основной турнир — только РПЛ;
- prediction engine рассчитывает числа;
- AI-агент объясняет прогноз и отвечает по имеющимся данным;
- все неопределённые продуктовые решения ведутся в `docs/PRODUCT_QUESTIONS.md`.

---

## 1. Идея

**RPL AI Agent** — веб-приложение в формате AI-аналитика российского футбола. Пользователь выбирает матч РПЛ или задаёт вопрос в свободной форме, а система показывает вероятности исходов, прогноз счёта, ключевые факторы и объяснение человеческим языком.

Главный принцип продукта:

> **Модель считает, AI объясняет.**

LLM не должна придумывать вероятности. Числовой прогноз формируется отдельной статистической/ML-моделью, после чего AI получает рассчитанные данные и превращает их в понятный разбор.

---

## 2. Целевая аудитория

### Основная
- болельщики РПЛ;
- пользователи, интересующиеся футбольной статистикой и прогнозами;
- аудитория спортивных Telegram-каналов и медиа;
- пользователи, которым нужен быстрый понятный разбор матча вместо ручного изучения статистики.

### В дальнейшем
- футбольные блогеры и каналы;
- спортивные медиа;
- B2B-клиенты, которым нужен API или white-label аналитический виджет.

---

## 3. Позиционирование

Продукт не должен выглядеть как «капперский бот» с обещанием гарантированного выигрыша.

Позиционирование:

**AI-аналитик РПЛ, который оценивает вероятности матчей и объясняет свой прогноз на основе данных.**

Ключевое отличие:
- объяснимость;
- прозрачная история прогнозов;
- специализация на российском футболе;
- возможность задавать вопросы о конкретном матче;
- автоматическое обновление данных.

---

## 4. MVP

Первая версия должна быть максимально простой и демонстрировать полный пользовательский сценарий.

### Обязательные функции

1. Главная страница в тёмно-синем спортивном стиле.
2. Список ближайших матчей РПЛ.
3. Выбор матча.
4. Вероятности:
   - П1;
   - X;
   - П2.
5. Прогноз наиболее вероятного счёта.
6. Уровень уверенности модели.
7. Ключевые факторы прогноза.
8. AI-чат по выбранному матчу.
9. Турнирная таблица.
10. Форма команд за последние 5 матчей.
11. Бомбардиры.

На первом этапе допустимы mock-данные.

---

## 5. Пользовательский сценарий

1. Пользователь открывает сайт.
2. Видит ближайшие матчи РПЛ.
3. Выбирает, например, «Зенит — Спартак».
4. Получает:
   - П1 — 45%;
   - X — 28%;
   - П2 — 27%;
   - прогноз счёта 2:1;
   - уверенность 64%.
5. Ниже видит объяснение ключевых факторов.
6. Может спросить AI:
   - «Почему Зенит фаворит?»;
   - «Какая форма у Спартака?»;
   - «Что сильнее всего повлияло на прогноз?».
7. AI отвечает, используя только доступные данные и результаты модели.

---

## 6. Архитектура

```text
Football API
     ↓
Data ingestion / normalization
     ↓
PostgreSQL / Supabase
     ↓
Feature engineering
     ↓
Prediction model
     ↓
P1 / X / P2 + score + confidence
     ↓
AI explanation layer
     ↓
Streamlit Web App
```

### Разделение ответственности

#### `src/data.py`
- получение данных;
- mock-данные для MVP;
- позднее — Football API и БД;
- нормализация структуры команд, матчей, таблицы и статистики.

#### `src/predictions.py`
- расчёт вероятностей П1/X/П2;
- прогноз счёта;
- confidence;
- позднее — Elo, Poisson, CatBoost/LightGBM или ансамбль.

#### `src/ai_agent.py`
- формирование контекста для LLM;
- ответы на вопросы пользователя;
- объяснение прогноза;
- запрет на самостоятельное изменение рассчитанных моделью вероятностей.

#### `src/components.py`
- UI-компоненты;
- карточки матчей;
- таблицы;
- блоки вероятностей;
- графики;
- чат.

#### `app.py`
- композиция страниц;
- состояние выбранного матча;
- маршрутизация пользовательского сценария.

## 7. Данные

### MVP
Использовать mock-данные, чтобы сначала проверить UX и структуру приложения.

### Следующий этап — тест API-Football Free

Первым реальным источником данных выбран **API-Football Free**. До покупки платного тарифа необходимо проверить фактическое покрытие РПЛ по инструкции `docs/API_FOOTBALL_TEST.md`.

На тесте подтвердить наличие:
- расписания;
- результатов;
- команд;
- турнирной таблицы;
- устойчивых team/fixture ID;
- домашних/гостевых матчей;
- при наличии — статистики матчей, составов, игроков и травм.

**Правило:** UI и prediction engine не должны напрямую зависеть от сырой структуры API-Football. Между внешним API и приложением должен быть слой клиента/нормализации.

До подтверждения покрытия не считать расширенные поля обязательными для MVP и не покупать Pro.

### Потенциальные признаки модели
- последние 5–10 матчей;
- голы забитые/пропущенные;
- домашняя и гостевая форма;
- Elo-рейтинг;
- положение в таблице;
- сила последних соперников;
- дни отдыха;
- xG/xGA при наличии;
- удары и удары в створ при наличии;
- травмы/дисквалификации при наличии качественного источника.

## 8. Prediction Engine

### Версия 1
Простая эвристика или mock-прогноз для демонстрации интерфейса.

### Версия 2
- Elo для оценки силы команд;
- Poisson для оценки распределения голов;
- комбинация этих оценок для P1/X/P2.

### Версия 3
ML-модель:
- CatBoost / LightGBM / Logistic Regression;
- обучение на исторических матчах;
- time-based train/test split;
- без утечки будущих данных.

### Метрики
Нельзя оценивать систему только по проценту угаданных исходов.

Нужно хранить:
- accuracy 1X2;
- log loss;
- Brier score;
- calibration;
- количество прогнозов.

Все опубликованные прогнозы должны сохраняться до начала матча и не изменяться задним числом.

---

## 9. AI Agent

AI получает структурированный контекст:

```json
{
  "match": "Зенит — Спартак",
  "prediction": {
    "home": 0.45,
    "draw": 0.28,
    "away": 0.27,
    "score": "2:1",
    "confidence": 0.64
  },
  "factors": [],
  "team_form": {},
  "standings": {}
}
```

AI должен:
- объяснять прогноз;
- сравнивать команды;
- отвечать на вопросы по переданным данным;
- указывать неопределённость;
- не гарантировать результат;
- не придумывать отсутствующие статистические факты.

## 10. UI / дизайн

Стиль:
- тёмно-синий фон;
- современный спортивный dashboard;
- белый/светлый текст;
- синие акценты;
- минимальное количество визуального шума;
- основной фокус — прогноз выбранного матча.

### Верхняя область
- название `RPL AI Agent`;
- подпись `AI-аналитик российского футбола`;
- справа место под логотип РПЛ 2026/27.

### Основной экран
Слева / по центру:
- ближайшие матчи;
- выбранный матч;
- прогноз;
- AI-разбор;
- чат.

Справа:
- таблица;
- форма команд;
- бомбардиры.

---

## 11. Что не делать в MVP

Не добавлять до проверки основной идеи:
- мобильное приложение;
- сложную авторизацию;
- собственную нейросеть;
- live betting;
- десятки турниров;
- сложную микросервисную архитектуру;
- Kubernetes;
- real-time websocket инфраструктуру;
- собственную админку.

## 13. Критерии готовности MVP

MVP считается готовым, если:

- приложение запускается одной командой;
- есть минимум 3 матча;
- выбор матча обновляет весь анализ;
- отображаются P1/X/P2;
- отображается прогноз счёта;
- отображается confidence;
- AI-чат использует данные выбранного матча;
- таблица и форма отображаются без ошибок;
- приложение адаптировано под desktop и приемлемо выглядит на мобильном экране;
- отсутствуют критические ошибки;
- README содержит понятный запуск для новичка.
